## 一、它解决什么问题

盯盘台 v2 解决了「**看得见**」,但没解决「**知道该干什么**」。
用户在 v2 里能同时看到 K 线、均线、资金流、AI 解读,却仍然要自己把它们翻译成一个动作。

v3 补的就是这层翻译,而且**必须满足三个约束**:

| 约束 | 为什么 | 怎么落 |
| --- | --- | --- |
| **零 LLM** | LLM 要等、要花钱、会编、同样输入可能不同输出;下单依据不能靠它 | 纯函数判定器,秒级、零费用、结果可复现 |
| **零编造** | 少一个数字就可能让人按错价下单 | 任一输入缺失 → 字段为 `None` + 写进 `degraded`,不拿 0 顶替 |
| **不与自身矛盾** | 同一张卡里既说「可以建仓」又说「不要抄底」,等于没说 | 本次实跑评审修掉 3 处矛盾(见 §五) |

## 二、版面:为什么放在右栏最顶部

```
┌────────────────────────────────────────────────────────────┐
│ 买股工具室 │ 自选 关注   上证 3735 +0.00% …                 │ 顶栏
├────────────────────────────────────────────────────────────┤
│ 全A 5,569 只 涨4078 跌1273 涨停24 跌停0 成交0.22万亿 …      │ 宽度条
├──────────────┬───────────────────────────┬─────────────────┤
│              │  标的 + 现价 + 涨跌       │  ① 操作决策      │
│  盯盘列表    │  分时/日K/周K/月K/60分     │  ② 持仓概览      │
│  (43 只)     │                           │  ③ AI 解读       │
│              │  K 线 + 均线 + 指标副图    │  ④ 新手速看       │
│              │                           │  ⑤ 领涨/领跌     │
│              │  关键价位                 │  ⑥ 两市量能      │
│              │                           │  ⑦ AI 问一问     │
└──────────────┴───────────────────────────┴─────────────────┘
```

**决策卡排第 ①(最顶部,在持仓概览之上)**,理由:

- 用户打开盯盘台问的第一个问题是「**我现在该干什么**」,不是「我手里有什么」;
- 持仓概览是**背景信息**,决策卡是**指令** —— 指令必须先于背景;
- 它不依赖「开始分析」按钮:选中股票即出,不必等 LLM。

### 响应式

- 三栏保持到 **1024px**(列表 236px + 图表 `1fr` + 右栏 268px),实测无横向滚动、决策卡无溢出;
- `< 1024px` 时右栏**不隐藏**,移到底部横排 —— 它是核心入口,不能因为窗口窄就消失。

## 四、配色纪律(踩过的坑都在注释里)

本项目约定 **红 = 涨/买/看多,绿 = 跌/卖/看空**(A 股红涨绿跌),与既有代码一致:
`DecisionColumn.tsx:164`、`PaperTradingPanel.tsx:264`、`tailwind.config.ts:71-74`。

| 元素 | 取色 | 为什么 |
| --- | --- | --- |
| 动作标签(entry/add/t_buyback) | `text-up`(红) | 方向色跟**动作**走 |
| 动作标签(exit/stop/t_sell) | `text-down`(绿) | 同上 |
| 状态徽标(`now`/`armed`/`blocked`) | **中性**(`text-text-pri` / `text-text-sec` / `text-text-ter`) | `status` 是**时态**不是方向。若 `now` 固定用红色,一个 `kind:'stop'`(无条件止损)、`status:'now'` 的动作会显示成红色「现在可做」—— 在红=利好的语境下是误导 |
| 「别动」 | `text-warn`(琥珀) | 琥珀只给预警 |
| 青色 `#22D3EE` | 只给选中态与焦点 | 不参与语义 |

> 这些取值**不要**因为「红色看着像危险」就改回去,代码注释里已写明理由。

## 五、实跑评审抓出并修掉的 3 处「自相矛盾」(commit `294ca6e`)

这三处都不是单元测试能发现的,只有**真机跑真实数据**才会暴露。

### 1. C2 的 `status` 与它自己的 `condition` 打架

```
现状:trig=下跌通道·延续 + do_not=下跌通道中不要抄底 + verdict=buy
      ▶ 超跌反弹建仓 [现在可做]
        触发: 站回 15.19 元(P20 低位带)且 KDJ 出金叉时小仓位试仓   ← 现价只有 14.35
```

- 根因:设计文档写 `status = 'now' if kdj.cross == 'golden'`,只判了 condition 的**一个合取项**,
  违反 §5 对 `now` 的定义(`now = 此刻条件已满足`);
- 修法:两个合取项都成立才标 `now`,否则 `armed` 并在 `basis` 写明还差哪一项。

### 2. 建仓候选不看通道 → 与「别动」清单互相打架

- 修法:新增「下跌通道守卫」—— `channel == 'down'` 时建仓候选一律降级 `armed`
  (§6.6 把该条列为**全局**规则,全局规则必须赢);
- 量化影响(30 只 × 120 交易日 = 3600 个信号日,真实 K 线):
  entry 触发日 **339 → 267 → 158**(仍 > 闸门要求的 100 条);
  通道分布 sideways 1658(46%) / down 1429(40%) / up 513(14%)
  → **四成建仓信号原本落在下跌通道**,这条守卫不是空转。

### 3. 拿不到实时价时,真实持仓被判成「空仓」

- 现象:第一次实跑 `002185.SZ` 返回「建仓参考 / 当前无底仓,做 T 前需先建仓」,
  而持仓表里明明有 **700 股 @ 23.04**;
- 根因:`stock.py` 的 `_resolve_position_status` 在 `current_price is None` 时直接 `return "empty"`。
  实时价缺失是**常态**(非交易时段 / 报价源抖动 / 报价与 K 线偏差 >10% 被降级);
- 后果:对一个**已深套**的持仓说「首仓 30%,可以建仓」;
- 修法:按 §5 的 `effective_price` 用 **K 线最新收盘价兜底**;持平归 `profit`
  (归 `empty` 同样会给出「建仓参考」误导);连兜底价都没有时保守取 `loss`
  —— 宁可给「解套参考 + 止损」,也不给「可以建仓」。

## 七、前端接入的两个坑(写在代码注释里)

1. **超时必须 60s**:`api.ts:23` 的 axios 默认 timeout 是 10000ms,
   而该端点串起 5 个外部数据源(实测冷启动 5.8~7.6s、稳态 0.55~1.5s)→ 10s 会直接超时,
   整卡永远显示「暂不可用」;
2. **切换股票有竞态**:用**请求序号守卫**(`decisionSeq`),A 的慢响应不得覆盖 B 的结果 ——
   否则决策卡会显示**另一只股票**的建仓价/止损价,股民照着下单是实打实的误导。

## 八、回测结论对卡面文案的约束（2026-10-21 回测后补记）

回测闸门跑完 5 轮迭代后（`docs/analysis/decision-backtest-report.md`），**卡面能承诺什么**被数据钉死了：

| 卡上内容 | 回测结论 | 约束 |
| --- | --- | --- |
| **止盈（exit）** | 通过闸门：信号后 10 日回撤比常态深 **+1.84%**（n=945） | 可以当作「有择时价值」的卖点讲 |
| **建仓（entry）** | **只有胜率价值，没有收益价值**：胜率 53.90% vs 基准 52.74%（+1.16pp，5 轮全为正），但 10 日平均收益 **低于**「随便哪天买并持有」（超额 −0.76%） | 卡面**只讲条件、价位与依据数字**，**不承诺收益**；不把「条件已满足」表述成「此时买入会赚钱」 |
| **止损（stop）** | 样本不足（n=30），不可判定 | 不在卡上宣称止损「有效」 |

**为什么这条约束重要**：这张卡的用户是拿着真钱盯盘的人。
「可以建仓」如果被当成收益承诺，而回测证明这批信号 10 日平均收益跑不赢随便哪天买，
那就是**用一个统计上不成立的优势去引导真实下单**。

**「赢小钱、亏大钱」的解释**：entry 信号挑中的票**更容易先涨 2%**（胜率更高），
但持有到期时平均收益更差 —— 说明它把「快涨一点」和「跌得更多」一起挑进来了。
这是**信号结构**的性质，不是阈值没调好：量比阈值在 [0, 2.0] 全区间扫过，
没有任何取值能同时满足「有效信号 ≥ 100 条」和「超额收益 > +1.0%」。

**未采纳的收紧**：回测侧的「C1 量比 ≥ 1.5 放量确认」**没有落到产品代码** ——
该配置下 entry 信号只剩 53 条（按 §10.2「不足则结论无效」），
却会把线上建仓触发率从 4.28% 压到 0.71%。
旋钮保留在 `backend/app/services/decision_backtest.py:EntryRule`，等扩样本后再复验。

## 九、与阶段 9「作战计划」的口径一致性

阶段 9 的明日预期与本卡的七问**共用同一套数字来源**（indicators / 报价 / 持仓），
因此两处结论必须一致。已核对：

| 场景 | 决策卡 | 作战计划 | 一致性要求 |
| --- | --- | --- | --- |
| 同一只票的建仓触发价 | `action.price` | `item.trigger_price` | 必须**逐位相同**（预案直接继承决策引擎算好的价） |
| 止损价 | `stop_loss.price` | `stop` 项的 `trigger_price` | 同上 |
| 大盘涨跌家数 | `market_env.market.up_total/down_total` | 明日预期的涨跌家数维度 | 同源同值 |
| 降级标注 | `data_quality.degraded` | `meta.degraded_reason` | 口径一致，**不得**一处标降级另一处不标 |

**原则**：作战计划**不重新计算**任何价格，只把决策引擎已算好的结论转成「明天什么价位做什么」。
若两处出现不一致，说明转换层引入了新的计算 —— 这违反「价格必须来自 indicators/报价/持仓或其显式四则运算」铁律，必须回改转换层。

**2026-10-22 实测核对结论**（真机跑一遍生成，plan_date=2026-10-22）：

| 核对项 | 结果 |
| --- | --- |
| `watch` / `unlock` / `exit` 项的 `trigger_price` vs 决策卡 `action.price` | 抽查 5 条，**逐位相同** |
| `stop` 项的 `trigger_price` vs 决策卡 `stop_loss.price` | 5 只持仓**逐位相同**（8.936 / 23.793 / 12.386 / 13.204 / 40.676） |
| 涨跌家数同源 | 两处同为「上涨 1981 家 / 下跌 3363 家」 |
| 降级口径 | `meta.degraded=false`、`outlook.degraded=false`、`review` 无降级标注 —— 三处一致 |

### 本轮记录的实现细节与已知边界（不改代码，只记录）

- **(f) `missing` 键的挂载位置**：决策层的 `missing` 键目前挂在 C3 的共用 `_guard({...})` 上，
  故 C3 的 armed/now 动作也带该键；转换层**只对 blocked 读它**，当前零影响。
  将来若有别的消费方读 `missing`，必须按 `status == "blocked"` 过滤。
- **(g) `diagnose.py` 的绕一跳（pre-existing 耦合，非阶段 9 引入）**：
  `backend/app/api/diagnose.py` 仍绕一跳取 `position_status` 的私有名
  （`_resolve_position_status` / `_kline_fallback_price` / `_sanitize_current_price`），
  而非从 `app/services/position_status.py` 直接导入。本轮不改，仅在台账注明。
- **(h) `battle_plan_service._load_transactions` 的 500 条上限（T6 评审发现）**：
  该函数用 `list_all(limit=500)` 再按日期过滤 —— 当某日流水**超过 500 条**时会漏单，
  漏掉的流水会让那笔操作被误判成「没执行」。
  当前规模（单用户自选 ≤ 20 只）远不到 500，属**低概率已知边界**；
  修法要动仓储层的分页/按日查询接口，超出阶段 9 范围，本轮不改，仅记录。
- **(i) 兑现统计口径**：`summarize_fulfillment` 的 `total` = **所有预案条数**
  （含 `n_a` 与 `no_data`），而 `executed + touched + missed` 不含它们 ——
  两者**故意不相等**。前端必须把「不适用 N」与「数据不足 N」显式列出，
  否则用户以为漏了几条。本轮已在 T8 的 ReviewCard 里补上这两项显示。
  另注：`no_data`（数据不足）是**独立第三态**，不是 `n_a`（不适用）的别名 ——
  「未触发」≠「没数据」。
- **(j) 纪律 note 用半角标点（展示层，不改）**：
  `"⚠️ 纪律问题:昨日标记别动/未解锁,今日仍有操作"` 用半角冒号 + 半角逗号，
  与本项目其余中文文案的「全角标点」风格不一致。
  属展示层，不改 —— 改了会让 `summarize_fulfillment` 里 `"纪律问题" in note`
  的判定依赖具体文案，徒增耦合。
