# ADR-0002:市场情绪统计改用「全市场翻页」,不再用首页采样

- 状态:**Accepted**
- 日期:2026-10-20
- 取代:无
- 影响范围:`backend/app/data/market_snapshot.py`(新增)、`backend/app/services/market_overview_service.py`、`backend/app/data/sina.py`、`backend/app/llm/minimax.py`、`backend/app/services/stock_advice_service.py`

## 背景

用户在真实使用中反馈「看不清楚市场、不知道怎么做投资决策」。排查后发现在市场概览页与首页情绪卡上
**展示的是失真数据**,而且 K 线与整条 AI 分析链路完全不可用。

本 ADR 记录这一轮排查出的 **5 个独立缺陷**及修复决策。

### 缺陷 1(最严重):涨跌家数是采样偏差的假数据

`fetch_market_sentiment()` 原来调用 `_fetch_hs_a_quotes(page_size=200)`,
而该函数用的是新浪 `Market_Center.getHQNodeData` 并带 `sort=changepercent&asc=0`
—— **按涨幅降序取首页**。于是取回的必然全是涨幅榜前列的股票,
却被当成「全市场」统计展示。

实测对比(2026-10-20 收盘):

| 口径 | sample_size | 涨 | 跌 | 涨停 | 跌停 |
| --- | --- | --- | --- | --- | --- |
| 旧实现(首页采样) | 100 | **100** | **0** | **93** | **0** |
| 新实现(全市场翻页) | 5568 | 3777 | 1667 | 59 | 10 |

首页里根本没有下跌股,「93 家涨停、0 家跌��」是**采样偏差的产物**,不是市场事实。
对小白用户来说这比没有数据更有害 —— 它会直接导致错误决策。

### 缺陷 2:涨跌停阈值不分板块

旧 `_bucket_pct()` 对所有股票用固定 ±9.9% 判定涨跌停。但 A 股的涨跌幅限制按板块不同:

| 板块 | 代码前缀 | 涨跌停 | 含 ST |
| --- | --- | --- | --- |
| 主板 | 600/601/603/605/000/001/002/003 | ±10% | ST ±5% |
| 创业板 | 300/301 | ±20% | ±20% |
| 科创板 | 688/689 | ±20% | ±20% |
| 北交所 | 8xx/4xx/920 | ±30% | ±30% |

后果:创业板/科创板 20% 涨停股被误判进 `up_5_10` 桶,主板 10% 涨停股又被当成「涨 5~10%」。
实测:按固定 10% 口径算出的涨停数 93,按板块口径是 59 —— **差了 34 家**。

### 缺陷 3:领涨/领跌恒为空

`fetch_market_movers()` 用 `sort=changeratio`。该字段名已不被新浪接口识别,
接口退化为按代码排序、且返回的 `changeratio` 字段为空 → `float()` 抛错 →
`continue` → 榜单恒为空数组。改成 `sort=changepercent` 即恢复。

### 缺陷 4:`kline_cache` 表在库里不存在(迁移已应用但表被删)

`data.db` 有 31 张表,唯独缺 `kline_cache`;而 `alembic_version` 已在 head。
即「迁移已应用,表后来被删」—— `alembic upgrade head` 认为无事可做,**不会自愈**。

后果:K 线接口与整条分析链路(指标计算 / AI 解读 / 分时图)全部 500:
`sqlalchemy.exc.OperationalError: no such table: kline_cache`

ORM 模型 `KlineCache` 本身完好,迁移 `a9b8c7d6e5f4` 也完好,只有库里的表没了。

### 缺陷 5:AI 解读因 JSON 被截断/语法错误而频繁失败

`/stock/{code}/analysis/stream` 报 `JSON 解析失败`。两个独立根因:

1. **截断**:`max_tokens=1500` 在 MiniMax `reasoning_split: True` 下是
   **思考链 + 正文的共享预算**。思考链吃掉大半后,正文 JSON 在约 1200 字符处被砍断
   (`Unterminated string starting at: line 1 column 1210`)。
2. **语法瑕疵**:即便给足 token,MiniMax 仍偶发单引号字符串 / 尾部多余逗号 /
   字符串内裸换行,或返回「前置自然语言 + 带缩进换行的格式化 JSON」
   (`Expecting value at line 1 column 1`)。实测带 `response_format={"type":"json_object"}`
   **也不能完全避免**。

## 决策

### 1. 全市场快照:新浪按代码升序翻页

新增 `backend/app/data/market_snapshot.py`:

- 接口:`Market_Center.getHQNodeData`,`node=hs_a`,**`sort=symbol`(代码升序)** + `asc=0`
  → 翻页稳定且**每页无重叠**(实测 56 页 5574 只,去重后 5568 只有效,无重无漏)
- 硬上限:单页最多 100 条(`num` 传任何值都只返回 100)
- 并发 10 页,56 页约 **3.4 秒**;内存缓存 60 秒
- **启动时后台预热**(`main.py:_warmup_market_snapshot`),
  避免首页第一次请求干等 5 秒 —— 实测首次请求从 5200ms 降到 **138ms**
- 数据源失败 → 抛 `MarketSnapshotUnavailable`,API 返回 502,**绝不返回假数据**

### 2. 涨跌停按板块判定

`market_snapshot.limit_pct(code, name)` 按上表返回该股当日涨跌停幅度,
`bucket_by_limit(pct, limit)` 据此分桶。判定容忍 0.1 个百分点浮点误差。

### 3. 领涨领跌修正

`sort=changepercent` + 兼容读取 `changepercent` / `changeratio` 两个字段名。

### 4. 补一张幂等的修复迁移

新增 `migrations/versions/f6a7b8c9d0e1_restore_kline_cache.py`:

- 表不存在 → 按 `a9b8c7d6e5f4` 完全相同的结构建表 + 建索引
- 表已存在(全新库按序跑迁移时会被老迁移先建出来)→ 跳过建表,仅确保索引存在

**幂等是必须的**:直接改已应用的老迁移会让全新库跑挂。

**根治(已补做)**:`app/db_migrations.py:ensure_schema()` —— 启动时在
`alembic upgrade head` 之后执行 `Base.metadata.create_all(checkfirst=True)`,
它**只建缺失的表、已存在的表一个字节不动**。于是:

- alembic 保证「已存在的表结构是最新的」
- create_all 保证「被删的表自动补回」

实测:手工 `DROP TABLE kline_cache` → 重启 → 日志
`schema 自检:发现缺失表 kline_cache —— 正在补建(迁移已应用但表被删的漂移)`
→ 表数 31 变 32 → K 线接口恢复 200。**以后这类漂移不用再手写补偿迁移。**

> 列级漂移仍归 alembic 管(create_all 不会给已存在的表加列)。
> 只存在于迁移而不在 ORM 的历史遗留表也不覆盖 —— 那属于迁移链问题,不是漂移。

### 5. LLM:五层修法

1. **max_tokens 给足**:`LLM_ANALYSIS_MAX_TOKENS = 4000`(原 1500),
   同时在 prompt 里加「输出务必精简,整份 JSON 不超过 1200 字」——
   给足预算 + 降低输出量,两头一起收
2. **provider 请求带 `response_format={"type":"json_object"}`**:
   让服务端尽量强制 JSON。**该参数不被所有模型/账号支持**,
   因此捕获 `HTTP 400 且响应体提到 response_format` 时去掉参数重试一次,降级为普通模式
3. **安全修复层**(`_repair_json_text`):用统一词法状态机只修**语法级**瑕疵:
   - 单引号字符串 → 双引号字符串
   - 字符串内裸换行/回车/制表符 → 转义
   - 字符串内裸双引号 → 转义(用「后面是否跟 `:` `,` `}` `]` 或 EOF」区分结束引号)
   - 去掉尾部多余逗号
   - **补回被漏掉的 JSON 分隔符**(2026-10-21 追加,见下方「缺陷 6」)
   - **不截取**「第一个 `{` 到最后一个 `}`」之间的内容(理由见下方纪律说明)
4. **修不动则严格重试**:用更严格指令重新调一次 LLM,重试结果**仍走严格解析 + schema 校验**。
   **流式与非流式两条路径都覆盖**(非流式原先只有解析、没有重试,本轮补齐)
5. **收紧超时预算**:`LLM_ANALYSIS_BUDGET` 300s → **150s**。
   实测正常耗时 20~35s(150s 仍有 4 倍余量),但偶发单次调用拖到 **499s**
   (300s 预算 + provider 重试/backoff)—— 用户要盯着转圈近 8 分钟。
   **超时越久不等于成功率越高**,快速失败并让用户点「重试」体验更好。

### 缺陷 6:LLM 偶发漏掉 JSON 分隔符(2026-10-21 追加)

浏览器实测跑通整条链路时,AI 解读偶发失败:

```
ai_error: JSON 解析失败: LLM 返回非法 JSON: Expecting ',' delimiter: line 1 column 303 (char 302)
```

**原日志只有异常信息,没有原文 —— 完全无法定位。** 于是先补了两件事:

1. **解析失败时把 LLM 原始输出落日志**(`_log_raw_on_parse_fail`,截断 4000 字)。
   没有原文就只能靠猜,这是排查的前提。
2. 加临时脚本循环打 SSE 端点复现,抓到原文:

```json
..."key_levels":[{"type":"support","price":13.47,"note":"近期低点支撑"},
{type":"stabilize","price":14.55,"note":"通道下轨企稳位"}],...
                    ↑↑↑ 这里
```

**根因:MiniMax M2.5 偶发漏掉对象键的「起始引号」**,写成了 `{type":"stabilize"`。
解析器停在 `type` 上,报 `Expecting property name enclosed in double quotes`。
严格重试换更严格的指令后仍失败(第二次是另一种畸形:成员间缺逗号)。

**决策:把这两种畸形补进安全修复层**,因为它们与已有的 4 条规则同属一类 ——
**只补分隔符,字面内容一个字节都不改,语义不可能变**:

| 畸形 | 原文 | 补后 | JSON 报法 |
| --- | --- | --- | --- |
| 漏掉键的起始引号 | `{type":"x"}` | `{"type":"x"}` | `Expecting property name enclosed in double quotes` |
| 成员间缺逗号 | `{"a":1 "b":2}` | `{"a":1, "b":2}` | `Expecting ',' delimiter` |

**为什么这两条判据不会误伤合法 JSON**:

- 合法 JSON 里,`"` 后面紧跟 `:` 的那个引号**必定是键的收尾引号**,
  而它一定是在「字符串内」状态被处理的 —— 所以当状态机在「字符串外」
  遇到一个后面跟 `:` 的引号时,它只可能是畸形产物。
- 合法 JSON 里一个值的后面只能跟 `,` `}` `]` 或空白,不会出现 `"` ——
  所以「值后面紧跟 `"`」必然是漏了逗号。
- **中文正文里的引号不能算作「值的结尾」**:如 `他说"重要"是`,
  若把中文字符算成值尾就会误插逗号,内容就变了。
  故「值尾」判定只认 ASCII 数字 / ASCII 字母 / `}` / `]`。

**为什么仍然不做「取花括号块」**:那是从非法输出里**捞**内容,
捞出来的片段未必是模型的完整结论。本轮修的是「内容原样、只缺一个分隔符」——
字面内容一字未改,不存在「捞」的问题。

> **纪律不变**:绝不用「花括号配对抽取」去捞非法 JSON 里的内容蒙混过关。
> 修复层只做不可能改变语义的语法修补,修完必须过 `_validate_analysis` 的 schema 校验 ——
> 垃圾内容无法冒充分析结果。
>
> **为什么连「取第一个 `{` 到最后一个 `}` 的完整块」都不做**:
> 那本质上仍是从非法输出里「捞」一段看起来像 JSON 的内容。前置自然语言
> ("以下是分析:")说明模型这一轮**没在遵循 JSON 模式**,捞出来的片段未必是它的完整结论 ——
> 蒙混过关比失败更危险。正确做法是**判失败 → 用更严格的指令让 LLM 重新输出一遍**。
> 项目既有测试 `tests/test_stock_advice.py::TestParseLlmJson` 本就是这么约定的
> (其文档写明「取消花括号配对提取,前置自然语言的格式不再被静默修复」),
> 本轮实现回归到该约定。

### 缺陷 7:前端三处静默失效(2026-10-21 UI 重设计时发现)

| 缺陷 | 现象 | 根因 |
| --- | --- | --- |
| **市场宽度色带 6 个档位家数全是 `undefined`** | 宽度条图例只显示「跌停 10 / 平 124 / 涨停 59」 | 后端返回 `up_5_10`,而 `snakeToCamel` 的通用规则 `/_([a-z])/g` 只吃「下划线+字母」→ 数字段名原样保留;但 `types.ts` 声明的是 `up5_10` → **类型全绿、运行期全 undefined**。同样影响大盘页「A 股涨跌分布」 |
| **所有卡片没有面板质感** | `Card` / `GlassCard` 渲染成无背景无边框的裸 div | `Card.tsx` 默认 variant 引用 `.panel`,而**整个前端没有 `.panel` 的定义** |
| **侧栏折叠偏好被断点覆盖** | 宽屏下 NavRail 强制展开成 200px | 断点监听在 `md` 以上执行 `setCollapsed(false)`,覆盖了「默认收起 + localStorage 偏好」 |

**决策**:
- `snakeToCamel` 加窄口径规则 `^([a-z]+)_(\d+)_(\d+)$ → $1$2_$3`
  (`up_5_10` → `up5_10`),`camelToSnake` 加对称规则。
  形态限定为「单词 + 两段数字」,不会影响其它键。
- `globals.css` 补 `.panel` / `.panel-hover` / `.panel-active` 定义。
- NavRail 断点改为**只收不放**(窄屏强制收起,宽屏不自动展开),手动切换后不再被断点干预。

### 缺陷 8:1024px 布局塌陷(2026-10-21 UI 重设计时发现)

设计稿初稿写「<1040px 时决策栏移到底部横排」。实测**做不到**:
决策栏是 `auto` 高度行,内容(持仓概览 + AI + 新手速看 + 领涨领跌 + 量能 + 问一问)
远高于视口 → `auto` 行吃光空间,把 `1fr` 行压成 **0 高度** →
**列表和图表整栏消失**(截图确认:1024px 下只剩决策栏)。

**决策**:三栏一直保持到 1024px(1024–1280px 收窄为 `236px / 1fr / 268px`,
操作按钮只留图标),窄于 1024px 才整体纵向堆叠。
**宁可收窄也不换行** —— 换行会让「动作链」断掉,正是这次重设计要解决的问题。

### 6. 顺带修的 CI 编码「问题」其实不存在

曾怀疑 `.github/workflows/ci.yml` 的中文是乱码,实测该文件是**合法 UTF-8**,
只是 PowerShell `Get-Content` 默认按 ANSI(GBK)读取导致的显示假象。**未做改动。**

## 为什么不用东方财富

东财 `push2.eastmoney.com/api/qt/clist/get` 更优(一次给 `total=5924`、`pz` 可放大)。
但实测在本机网络下:

- PowerShell / .NET `Invoke-WebRequest` → **200**,接口完全可用
- Python 栈(httpx 4 种组合 / urllib / 备用域名 `82.push2` `push2delay` `push2his`)
  → **一律** `RemoteDisconnected` / `Server disconnected without sending a response`

同环境下 Python httpx 访问新浪**完全正常** → 是目标站点的客户端筛选策略,与网络无关。

**结论**:后端是 Python 栈,东方财富不可用,改用新浪全量翻页。

> **注意**:ADR-0005 写的「东财被公司网络限流」在此结论下**已不准确** ——
> 它没被限流,只是 Python 栈连不上。**网络类结论会随时间漂移,不要当作既定事实。**

## 后果

### 正面

- 首页与大盘页展示的是**真实全市场口径**(5568 只),涨跌家数/涨停跌停可直接用于决策
- 领涨领跌恢复,情绪卡有真实数字
- K 线与分析链路从「全 500」恢复到可用
- AI 解读 JSON 解析成功率显著提升(修复层 + 严格重试双保险)
- 情绪接口首屏延迟 5200ms → 138ms(启动预热)

### 负面(必须承认)

- 全市场快照每次冷启要翻 56 页(约 3.4 秒)+ 56 次外部请求
  —— 已用 60 秒缓存 + 启动预热缓解,但这是用请求量换数据真实性
- 修复层会让「本该失败的畸形 JSON」被救回来 —— 代价是可能掩盖 prompt 质量问题,
  故保留了严格重试作为兜底路径
- 前置/后置自然语言**不再**被修复层捞出来(见决策 5 的纪律说明),这类输出会
  多消耗一次 LLM 调用走严格重试 —— 慢一点,但不会把不确定的片段当结论给用户
- LLM 超时收紧到 150s 后,极端长尾请求会更快失败(用户需点「重试」);
  这是刻意的取舍:体验优先于个别长尾的成功率

## 护栏

- `market_snapshot.py` 的 `limit_pct` / `bucket_by_limit` 是**板块感知的唯一实现**,
  不要在别处再写固定 ±10% 的判定
- 新增市场统计能力时,**禁止**用单页/首页采样冒充全市场统计;
  必须翻页取全量,或显式标注 `partial: true` 让前端提示「样本口径」
- LLM JSON 解析:严格解析 → 安全修复 → 严格重试,三步顺序固定,不要跳过 schema 校验
- **安全修复层只做语法级修补**;要加新规则时先问「它会不会改变 JSON 的语义」
  —— 会,就别加(改用严格重试)
- **解析失败必须留下原文**(当前实现:`_log_raw_on_parse_fail` 落 WARNING 日志)。
  只记异常信息等于没记 —— 报的是位置不是原因,没有原文只能靠猜。
- `snakeToCamel` 转换**数字段名**时要留意 `up_5_10` 这类形态:
  键名以数字结尾时,后端 snake_case 与前端 camelCase 的对应关系要写进测试
- `ensure_schema()` 只补**缺失的表**,不做列级变更;列级变更一律写 alembic 迁移
