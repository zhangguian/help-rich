## 一、为什么做这一期(实测证据)

上一期的验收标准全部通过,但**真机一跑就暴露出三个「数字在说谎」级别的问题**。
本文所有数字均为 **2026-10-31 全市场实测**(5574 只快照 → 成交额达标 1817 只 → 逐票精算),
不是估算,不是推测。

### 1.1 🔴 分组计数被全局 Top-60 截断扭曲 —— 91% 的命中人间蒸发

```
真实命中 663 条  →  入库只剩 60 条
  主力异动  真实 455  →  页面显示 47
  低  吸    真实 133  →  页面显示 10
  锁  仓    真实  58  →  页面显示  2   ← 差 29 倍
  高  抛    真实  17  →  页面显示  1   ← 差 17 倍
```

**根因**:`service.py:270` 的 `top = result.hits[:BEHAVIOR_SCREENER_TOP_N]`(TOP_N=60)
—— **全局按分数截断**。但四类信号的分数**本就不可跨类型比较**
(类型权重不同,主力异动权重最高),于是全局截断**系统性偏向高权重类型**。

**为什么这不是「编数字」但比编数字更隐蔽**:它没有凭空造一个值,
它让一个**真实数字(58)呈现出另一个数字(2)**,用户无从察觉。
违反的是项目铁律「缺数据 → 不产出,绝不编数字」的**精神**。

**连带失真**:批次表的 `total_picks` 存的也是截断后的 60,
所以页面上口径条的「命中信号 60」同样是假的(真实 663)。

### 1.2 🔴 找股页与 K 线图的信号窗口不对齐 —— 61% 的信号「有但看不到」

```
K 线图只回传最近 60 日的标注(BEHAVIOR_MARKERS_LOOKBACK_DAYS = 60)
找股页用 120 根日 K 的窗口,最远到 ~168 个日历天

→ 405 / 663 条(61%)、涉及 110 只股票:
  找股页列出来了,点进个股页 K 线上根本找不到那个标注
```

**分布实测**:
| 信号距今天数 | 条数 |
|---|---:|
| 0–29 | 110 |
| 30–59 | 144 |
| 60–89 | 131 |
| 90–119 | 119 |
| 120–149 | 95 |
| 150–179 | 64 |

**根因**(`api/kline.py:62`):K 线路径用**日历天**回看(60),
找股路径用**K 线根数**窗口(120 根 ≈ 168 日历天)—— 两边口径不同。
两条路径虽然共用同一个判定入口 `detect_behavior_markers` ✓,
但**输入口径不同**(K 线 300 vs 120 根、资金流 300 vs 120 天、回看 60 vs 120)。

> 这也是上一期 §6.5「闭环」的真实成色:闭环只验证了「同一条标注两边都在」,
> 没解决「**61% 的信号在 K 线上压根不存在**」。

### 1.3 🔴 候选池的筛选维度与被筛目标的时间窗错配

```
候选池:filter_universe() 后按「当日主力资金异动强度」降序 → 取前 120
打分对象:历史窗口内(最远 ~168 日历天)发生的异动信号
```

一只票 **20 天前有强信号、今天资金异动平淡** → **压根进不了候选池**,
打分再准也没用。上一期 L4 只写了「可能漏掉冷门但有信号的票」,
没指出这是**筛选维度与被筛目标的时间窗不匹配**。

### 1.4 🟠 盘中跑批基于未收盘的当日日 K

`fetch_klines` 在盘中返回的是**当日未收盘快照**。
`run_daily_scan` 走 `upsert_run`(同日覆盖),所以收盘后重跑会覆盖 ✓,
但**收盘前**用户看到的就是一份基于半根 K 线的结论,且被当作「最新批次」。

### 1.5 🟠 两套算法无一致性校验

找股批次落库、个股页标注实时算,两者应当逐字一致(同入口 + 尾窗口径),
但**没有任何断言或巡检**。数据缓存过期、窗口口径改动 → 两者悄悄漂移,
**不报错**,只是「同一只票在两个页面显示不同」。

### 1.6 🟡 阈值无回测(上一期 L1/L2)

阈值已用真机数据校准过一轮,但**无法回答「换市场环境是否仍成立」**。

### 1.7 附带发现:找股**没有自动跑批**

`run_daily_scan` 的唯一调用方是 `POST /trigger-now`,
而该端点默认被 `SCREENER_ALLOW_TRIGGER` 环境变量挡住 → **默认状态下找股页永远是空的**。
选股模块有 `start_screener_scheduler`(每日 15:30,`main.py:186` 已 spawn),找股没有对应调度器。

> 这条严格说属于「能不能用」而非「可信不可信」,
> 但它决定了**可信的数据从哪来**,故纳入闸 4。

## 二、设计总览:四道闸

```
闸 1 · 数字闸  口径诚实:分组计数用真实命中数,明细全量入库,不做全局截断
闸 2 · 完备闸  不漏 + 窗口对齐:去掉候选 120 截断;两边统一 120 日历天
闸 3 · 一致闸  两套路径逐条比对,pytest 守门 + 手动巡检脚本
闸 4 · 稳定闸  盘后自动跑批 + 批次记录数据时点 + 盘中结果显式标注
```

四道闸**互相独立、可分批落地**,任一闸单独上线都不破坏其余。

## 三、闸 1 · 数字闸(口径诚实)

### 3.1 口径定义

| 字段 | 现在的值 | 改成 |
|---|---|---|
| 批次 `total_picks` | 截断后的 60 | **窗口过滤后的真实命中总数**(实测前 663 / 过滤后 ≈400) |
| 分组 `count` | 入库条数(失真) | **该类真实命中数**(来自批次表) |
| 分组 `picks` | 每类 Top N | 每类**真实命中中按分数排序的前 N**(N=60) |
| 批次明细行 | 全局 Top 60 | **全部命中**(不再截断) |

### 3.2 数据模型变更

`BehaviorSignalRun` 新增三列(详见 §八):

| 列 | 类型 | 含义 |
|---|---|---|
| `hit_counts_json` | TEXT | `{"main_force_move": 268, "dip_buy": 96, ...}` 每类**真实**命中数(过滤后) |
| `data_as_of` | DATE | 本批数据截止日(已收盘的最后一个交易日) |
| `is_intraday` | BOOLEAN | 本批是否含**未收盘**的当日 K 线 |

`BehaviorSignalPick` **不变**(明细行本来就够用)。

### 3.3 落库口径

```python
# service.py · run_daily_scan
hits = result.hits                       # ← 不再 [:TOP_N] 截断
counts = Counter(h.kind for h in hits)   # ← 真实分类计数
run = await repo.upsert_run(
    target,
    ...,
    total_picks=len(hits),               # ← 真实总数
    hit_counts_json=json.dumps(counts, ensure_ascii=False),
    data_as_of=..., is_intraday=...,
)
await repo.replace_picks(run.id, [ ... for h in hits ])   # ← 全量
```

⚠️ **闸 2 的时间窗口过滤发生在 `scan_market` 内部**(产出 `hits` 时就滤掉),
**不在落库时滤** —— 否则批次表里存的仍是超窗口信号,只是展示时被藏起来,
`count` 与明细依然对不上(那就把问题从「展示层」挪到了「存储层」,没解决)。

**存储量估算**:闸 2 加了 120 日历天窗口过滤后,实测命中会从 663 条收敛到 **≈400 条**
(推算值,实施时实测)→ 年增约 15 万行,每行含 `metrics_json`(约 200~400 字节)
→ **年增约 50 MB**。SQLite 完全承受得住(当前 `data.db` 已 122 MB)。
**不做保留策略**(YAGNI);真要控制体积,加一个按月归档即可。

### 3.4 API 形状变更

`GET /api/behavior-screener/latest` 的响应(**示例值,实际数字以实施后实测为准**):

```jsonc
{
  "run": { "runDate": "2026-10-31", "totalPicks": 402,
           "hitCounts": { "main_force_move": 268, "dip_buy": 96, ... },
           "dataAsOf": "2026-10-31", "isIntraday": false },
  "groups": [
    { "kind": "main_force_move", "kindLabel": "主力异动",
      "count": 268,              // ← 真实命中数(不是 picks 长度)
      "picks": [ ...该类前 60 条... ] }
  ],
  "all": [ ...跨类合并的前 60 条... ]
}
```

⚠️ **响应体控制**:全量 400 条若一次性返回,约 160 KB → 前端一次渲染 400 行会卡。
→ `/latest` **只返回每类前 60 条**(跨类合并的 `all` 同样取分数前 60),
真实总数靠 `count` / `totalPicks` 字段披露;
需要看更多时用新增参数 `?kind=<kind>&limit=<n>&offset=<n>` 拉取。

### 3.5 前端

- 口径条「命中信号」改读 `run.totalPicks`(真实数)
- 每张分组卡标题显示 **真实 count**,下方明细注明「按分数列出前 60 条 / 共 N 条」
- 新增「展开更多」→ 调 `?kind=&limit=&offset=` 追加渲染
- ⚠️ 前端 API 类型**必须写驼峰**(`hitCounts` / `dataAsOf` / `isIntraday`)
  —— axios 拦截器会递归 snake→camel,写 snake_case 时 TS 不报错但运行期全是 `undefined`

## 四、闸 2 · 完备闸(不漏 + 窗口对齐)

### 4.1 候选池:去掉 120 截断

```python
# 现在
precands = candidates[:candidate_limit]     # ← 截断到 120
# 改成
precands = candidates                        # ← 成交额闸门保留,不截断
```

**成交额闸门(`POOL_MIN_AMOUNT_YI`)保留**:成交额 < 1 亿的票流动性差,
信号本身也难以被可靠观测 —— 这是**合理的业务闸门**,不是口径错配。
去掉的是**「取前 N」这个人为上限**。

**参数语义**:`scan_market(candidate_limit=...)` 的默认值从 `120` 改为 `None`
(= 不截断);保留该参数是为了**测试与小规模验证**(分级验证时传 300 / 600)。

**实测外推**:30 只冷缓存 0.87s(零失败)→ 29ms/只 → 1817 只 ≈ **53 秒**。

⚠️ **必须先小规模验证外网承受力**:1817 次外网请求打同一个新浪接口,
是 30 只实测的 60 倍。**分级验证(300 → 600 → 1817),任一级失败率超阈值即停**,
不靠推演说「应该没事」。

### 4.2 时间窗口统一:两边都按 120 个**日历天**

⚠️ **关键**:现在两边口径单位都不同(根数 vs 日历天),必须统一到**日历天**。

| 路径 | 现在 | 改成 |
|---|---|---|
| K 线路径 | `BEHAVIOR_MARKERS_LOOKBACK_DAYS = 60` | **120** |
| 找股路径 | 不按时间过滤(全 120 根 K 线) | 过滤 `days_ago <= 120` |

**为什么选日历天**:与用户看到的时间语义一致(「3 个月前」),
且与 K 线图的回看参数是同一个概念,不会出现「120 根 ≈ 168 天」这种换算歧义。

**改后命中数**:实测分布里 0–29(110)+ 30–59(144)+ 60–89(131)+ 90–119(119)
= 504 条落在 120 日历天内,120–149 天那 95 条里约 3/4 在窗口内
→ **预计约 400 条**(实施时以实测为准,写进验收)。

> ⚠️ **命中数会「变少」是预期的**:660 条里有 159 条(>120 日历天)被窗口过滤掉了。
> 它们本来就不该出现在「近期异动」榜单里 —— 旧版让它们占着 Top 60 的位置,
> 才是闸 1 要修的「挤榜」。**不是丢信号,是把它们放回 K 线图的历史标注里**。

**连带效果**:>120 日历天的老信号不再挤榜(它们原本占 95+64=159 条),
闸 1 的「真实 count」与「明细前 60」的差距也随之收敛。

### 4.3 K 线端点响应体影响

标注从 60 天扩到 120 天 → 标注数可能翻倍 → 响应体从实测 52 KB 上涨。
**实施时实测**响应体大小与前端渲染耗时;若超阈值,改为「回传全部标注但限制每类条数」。

## 五、闸 3 · 一致闸(巡检)

### 5.1 要守住的不变量

给定**同一只票**,两条路径必须产出一致的标注:

```
路径 A(找股):fetch_klines(count=120) + fetch_flow_daily(count=120)
               → align_by_date → detect_behavior_markers
路径 B(K 线):fetch_klines(count=300) + fetch_flow_daily(count=300)
               → align_by_date → detect_behavior_markers → 回看窗口过滤
```

**断言**:
- `S_A ⊆ S_B`(找股路径的信号必须都能在 K 线路径找到)——**这条是硬门槛**:
  违反即说明「找股页列了、但 K 线上找不到」又出现了
- 两者都成功时 `S_A == S_B`,且每条的 `kind / date / metrics / reason` **逐字一致**
- 某一路数据获取失败时,退化为 `⊆` 并**显式标记该票为「不可比对」**(不静默跳过)

这正是「尾窗口径 + 同一判定入口 + 同一回看窗口」该保证的不变量 —— 现在**没有任何测试钉它**。

> ⚠️ **基准日必须一致**:两边的「今天」都取 **`run_date`(跑批日)**。
> K 线路径现在用的是「K 线末根日期」(`api/kline.py:58`),盘中两者相同、
> 但停更/停牌时可能不同 → 实施时统一为「传入的基准日」,不留两套口径。

### 5.2 两层巡检

| 层 | 形式 | 触发 | 覆盖 |
|---|---|---|---|
| **单元守门** | `tests/test_behavior_consistency.py` | 每次 pytest | 固定 3 只样本(K 线 + 资金流 fixture),比对两项不变量 |
| **端到端巡检** | `scripts/verify_behavior_consistency.py` | 手动 / 盘后批后 | 真实数据,随机 N 只(默认 50),输出**差异表**(票/日期/类型/字段/两边的值) |

**端到端脚本的输出格式**(必须可读,不能只给「不一致」):

```
stock_code | kind | date | 字段 | 找股路径 | K线路径
000568.SZ  | main_force_move | 2026-10-20 | r0x_ratio | 73.0 | 71.8
```

### 5.3 一致性巡检发现差异时怎么办

**不自动改数据**,只报告。差异意味着两个口径分叉了 → 人工判断哪边对 →
修代码 → 重跑。**绝不在运行时静默取其一**(那会让「不一致」变成「永远看不见」)。

## 六、闸 4 · 稳定闸(调度 + 时点)

### 6.1 调度器

照搬选股的 `start_screener_scheduler`(`modules/screener/service.py:414`),
落在 `modules/behavior_screener/service.py`:

```python
async def start_behavior_scheduler() -> None:
    """每日 15:30 后跑一次(工作日;今天已有**非盘中**批次则跳过)"""
```

⚠️ **与选股的一处关键差异**:
选股的跳过条件是「今天有 run 就跳过」;
behavior **不能这样** —— 盘中手动跑过的那份带 `is_intraday=true`,
若被当成「今天已跑」,盘后调度器就会跳过 → **盘中那份会一直留着当最新批次**。

→ 跳过条件必须是:「今天的批次存在 **且** `is_intraday == False`」。

`main.py` 里对应 `_spawn(start_behavior_scheduler())`。

### 6.2 `data_as_of` 与 `is_intraday`

| 字段 | 精确含义 |
|---|---|
| `run_date` | 批次归属日(已有) |
| `data_as_of` | 本批数据中**已收盘**的最后交易日 |
| `is_intraday` | 本批**是否额外包含**当日未收盘数据 |

| 场景 | `data_as_of` | `is_intraday` |
|---|---|---|
| 盘后自动跑(15:30 后) | 最近一个**已收盘**交易日 | `False` |
| 盘中手动跑 | 最近一个**已收盘**交易日(不含当日) | `True` |
| 盘中跑批后又盘后跑 | 同上 | `False`(覆盖) |

判定复用既有的 `behavior_fund_flow_service._is_post_close()`(工作日 15:00 后)。

> `data_as_of` 与 `is_intraday` 分开的原因:单看 `data_as_of` 无法区分
> 「盘后跑的完整数据」与「盘中跑的半成品」—— 而这正是用户最需要知道的区别。

### 6.3 前端明示

盘中批次,找股页口径条加一行:

> ⚠ 本批次含**未收盘**的当日数据(盘中跑批),收盘后会自动重算。

这不是免责声明,是**事实披露** —— 与项目「如实披露每一级真实数字」的口径一致。

## 八、数据模型变更汇总

`backend/migrations/versions/<rev>_add_behavior_trust_fields.py`

```python
op.add_column("behavior_signal_run", sa.Column("hit_counts_json", sa.Text(), nullable=True))
op.add_column("behavior_signal_run", sa.Column("data_as_of", sa.Date(), nullable=True))
op.add_column("behavior_signal_run", sa.Column("is_intraday", sa.Boolean(), nullable=True))
```

- `down_revision` = `b3c4d5e6f708`
- ⚠️ **表名是 `behavior_signal_run`（单数）** —— 已于 2026-10-31 实测确认（`sqlite_master` + ORM `__tablename__`）。
- 新列全部 nullable / **无默认值** → **存量批次行不需要回填**，且省略该列时自然落成 `NULL`（未知）。
- 🚨 **`is_intraday` 不设 `server_default`**（2026-10-31 human 拍板）：设 `DEFAULT 0` 等于把「未知」
  编码成「确定不是盘中」，与项目铁律「缺数据 → 绝不编数字」冲突。`NULL` = 未知，
  与 `hit_counts_json` / `data_as_of` 的 `None` 语义一致；生产端必须显式传真值。
