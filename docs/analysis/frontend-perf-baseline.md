### 一个差点漏掉的坑:助手流式输出会把盯盘页拖着重渲染

盯盘页要消费助手 context 才能拿到「当前选中票」。如果它消费的是**完整** context,
助手每吐一个 token 都会改 `messages` → context value 变化 → **盯盘页整页重渲染**
(44 行列表 + 14 张图)—— 上面那三项验收的好成绩会被直接打回去。

**修法**:把 context 拆成两份 ——
「动作 context」(只含引用稳定的回调,value 永远不变)给盯盘页用,
「状态 context」(messages / mood / sending)只给悬浮球和对话框用。

**验证**(脚本 `tb_stream_rerender_check.js`,助手流式输出期间采样):

| 指标 | 结果 |
| --- | --- |
| 流式期间 long task | **0 条** |
| 盯盘列表 DOM 是否变动 | **否**(行内容逐字未变) |
| 图表 canvas 是否被重建 | **否**(14 → 14) |
| console error | 0 |

### 各档改了什么

- **C 十字光标(P2)**:`handleCrosshair` 不再每次 `mousemove` 直接 `setHoverValues`。
  改成「读数先存 pending → rAF 合并到帧 → 两次落盘至少隔 60ms」;
  `legendRows` 改 `useMemo(依赖 indicators / COLOR)`——这两者本来就是稳定引用,
  所以图例结构不再跟着光标读数一起重建。
  复测用**带确证信号**的脚本(光标确实触发、图例读数确实从 `—` 变成真实值),不是假绿。
- **D 轮询(P1)**:加了**在途保护**(上一轮没跑完就跳过)、**可见性暂停**
  (`visibilitychange` 隐藏时停)、**内容没变就不 setState**(用 `JSON.stringify`
  求内容签名,签名相同就保留旧引用 → 零重渲染)、**分档频率**
  (报价/指数 15s,情绪 60s)、**失败退避**(15s → 22.5s → 30s 封顶)。
  另外把 `/market/overview` 与 `/market/sentiment` **拆开**——
  原来注释写着「拆开让指数先出」,代码里却还是 `Promise.all`,
  情绪接口服务端要 2.5s,把整个大盘速览拖住了;拆开后指数 ~1.4s 就到。
- **D 顺带删掉一个死状态**:`quotesMap` 全文件只有声明和赋值、**从来没有被读过**,
  却让每轮轮询多触发一次全页重渲染。
- **A 首屏**:见 §5。

## 5. 已知未解决项(诚实记录)

> ⚠️ 本节已在**第三轮**(§6)里被实测推翻并重写。原记录是「首屏那条 200–500ms 的长任务没解决,
> 波动极大(216/472/521/573ms)」。第三轮用归因方法测出来的结论是:
> **真正的大头不在首屏,而在「切票」这一步(710ms),而且它是可修的。**
> 首屏那条长任务在第三轮复测里只有 **167ms**。原记录保留在下面,作为「测量纪律」的教材。

**首屏那条 200–500ms 的长任务没解决**,而且**波动极大**(同一份代码测出 216 / 472 /
521 / 573 ms)。它出现在导航后 43~63ms,即 **React hydration + 首屏渲染**阶段。

已排除的嫌疑(用数据排除,不是猜):

- **不是列表行的布局动画**:把 `WatchList` 每行的 `motion.li layout` 去掉后重测,
  首屏 521ms —— 与保留时的 472ms 落在同一噪声区间,**没有改善**。
  → 已把 `layout` 改回去,不白丢一个排序动效。
- **不是 framer-motion 的包体**:它只占共享 JS 87.5 kB 的一部分,且不影响长任务归属。

剩下的怀疑方向(**本轮未做**,因为它不在计划项里、且超出「前端性能」到「架构」的边界):

1. **44 行 × 14 个 canvas 的首屏一次性挂载**(K 线 + 10 组指标 + 成交量 + MACD/KDJ)。
   lightweight-charts 建 series + 算指标是同步的重活。
2. **SSR → CSR 的 hydration**:`next start` 下 React 要把服务端 HTML 接管成活组件。
   首屏那 44 行是 SSR 出来的,hydration 时要在客户端重跑一遍。

可行的后续方向(需要单独排期):

- 首屏只渲染**可视区域**的行(virtualization),滚动时再挂剩下的;
- 图表改成**按需初始化**(先出价格,指标延后一帧);
- 把 K 线区改成 `next/dynamic` + `ssr: false`,减少 hydration 负担。

**在动手之前应该先测**:用 PerformanceObserver 把首屏长任务拆到组件级别,
确认到底是 canvas 初始化还是 hydration 占大头 —— 否则又会变成「凭感觉改」。
（这正是本轮 P2 的教训:先测,再改;改完再测。）

## 6. 第三轮:切票 710ms 的归因与修复(P6 / P7)

> 起因:第三轮复测时,C 档(十字光标)冒出 **38 条 ~1000ms 的长任务**,
> 与文档里记的「0 条」完全对不上。**与代码无关的怀疑先被一一排除**,
> 过程中反而挖出两个真问题。

### 6.1 归因方法(可复用)

| 手段 | 作用 | 本轮结论 |
| --- | --- | --- |
| **资源时序对齐** | 把 long task 的 `start` 与 `resource.start/responseEnd` 排在一起 | 长任务 `start=20211` **早于所有请求** `start=20920` → 卡的是**同步渲染**,不是接口 |
| **对照实验** | 点**同一只票**(状态不变)vs 点**另一只票**(状态变化) | 同票 0 条 → 差异全在「选中态变化」这条路径 |
| **LoAF**(`long-animation-frame`) | 给**脚本级**归因(`longtask` 只有 `window`,没用) | 长帧时间几乎全在 `styleAndLayout`,帧里是 React 的 `MessagePort.onmessage` + 图表的 `FrameRequestCallback` |
| **canvas 尺寸探针** | 验证「ResizeObserver ↔ applyOptions 反馈循环」假设 | 5 秒内 14 张 canvas 尺寸变化 **0 次** → **假设被否** |
| **rAF 帧率探针** | 判断测出来的延迟是**应用**的还是**环境**的 | 5 秒只有 **6 帧**(1.2fps) → 环境被降频 |

### 6.2 P6 · 自选列表行 memo 化(真问题,已修)

**根因**:44 行自选是**内联 `motion.li`**(带 `layout`)且**没有 memo**。
`activeCode` 一变 → 44 行全部重渲染 + framer-motion 投影系统全量测量 →
点击瞬间 **710ms 主线程阻塞**。

**修法**(`components/watch/WatchList.tsx`):

1. 行抽成模块级 `WatchRow = memo(...)`(rail / panel 两种形态一起抽);
2. 行用到的回调**全部引用稳定**:`onContextMenu` / `onOpenMenu` / `openSetPos` /
   `toggleFavorite` 改 `useCallback`,`onChanged` 用 ref 转一手
   —— **任何一个每次渲染新建,memo 的浅比较就失配,memo 白做**;
3. `motion.li layout` **保留**(P5 已实测:去掉它对首屏无改善,排序动效是刻意留的)。

**效果**(同一环境、同一脚本、前后对比):

| | 切票长任务 |
| --- | --- |
| 改前 | **1 条 × 710ms** |
| 改后 | **0 条** ✅ |

### 6.3 P7 · 自动刷新倒计时挪进独立 store(真问题,已修)

**根因**:倒计时 `secondsLeft` 只被顶栏一个「自动刷新 15s」小按钮用到,
却住在 `Workbench` 的 state 里 → **每秒一次 `setState` → 整页重渲染**
(44 行自选 + 14 张图 + 三栏布局全走 React diff + 样式重算)。
LoAF 里长帧时间几乎全在 `styleAndLayout`,与此吻合。

**修法**:新增 `stores/useRefreshStore.ts`(zustand,沿用 `useIntradayStore` 的写法),
`page.tsx` 不再持有该 state,`DeskTopBar` 自己订阅 → **每秒只有那个按钮重渲染**。

## 7. 测量环境的坑(这一节比数字更重要)

第三轮踩了四个坑,每一个都造出过「看起来很好」或「看起来很糟」的**假数据**。

| 坑 | 现象 | 处置 |
| --- | --- | --- |
| **Service Worker 缓存旧 bundle** | 刚 `npm run build` 完去测,量的是**上一版代码** | 测量前先 `navigator.serviceWorker.getRegistrations()` 注销 + `caches.keys()` 清空 + reload |
| **`NEXT_PUBLIC_*` 是构建期注入** | 重建时没带 `NEXT_PUBLIC_API_URL` → bundle 里是 `.env.local` 的旧端口 → 全部 API `ERR_CONNECTION_REFUSED` → 列表一行都不渲染 → **测出「0 长任务」的假绿** | 重建时显式设环境变量;**并断言 `rowsReady`**(列表真的有 ≥10 行)才采信数字;可 `grep .next/static/chunks/*.js` 确认嵌进去的地址 |
| **固定 `waitForTimeout` 不可靠** | 首屏数据有时 9s 到、有时 16s 到、有时 60s 都不到 | 用 `waitForFunction` 等真实条件,并把 `rowsReady` 打进结果 |
| **无头/后台浏览器被降频** | rAF 只剩 1.2fps → 每次交互等 1 秒 → 长任务被放大成 ~1000ms | **每次测量前先量 rAF 帧率**;帧率 < 30fps 就把「墙钟延迟」标成不可用,只信 longtask 口径 |

**由此得到一条通用纪律**:
> 任何「前端性能测量」,先证明 **① 页面真的加载了数据 ② 浏览器没被降频**,
> 再看数字。少了这两步,测出来的既可能是假绿,也可能是假红。

### 7.1 想知道「真实前台」的数字,怎么做

Tabbit 的 `foregroundPolicy=preserve` 不允许把标签页置前(`page.bringToFront()` 会被拒),
`--foreground` 也只在 `create/tabs` 阶段可用。两条可行路子:

1. **用 LoAF + longtask 口径**,不看墙钟 —— 应用侧有没有阻塞,这个口径不受降频影响;
2. **用真实浏览器**(可见窗口)手工复测,并用「每步耗时」自证帧率正常
   (正常应 < 20ms/步;本环境是 1003ms/步)。

## 8. 复测方法

```powershell
# 1) 后端(隔离实例,避免与他人会话抢端口)
$env:DATABASE_URL='sqlite+aiosqlite:///./.pytest_tmp/isolated.db'
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8010

# 2) 前端 prod
#    build 前必须先停 dev(两者共用 .next)
#    ⚠️ NEXT_PUBLIC_API_URL 是**构建期注入** —— 重建时必须显式带上,
#       否则会用 .env.local 里的旧端口(8000)→ 整页连不上后端 → 测出假绿
$env:NEXT_PUBLIC_API_URL='http://127.0.0.1:8010/api'
npm run build
npm run start -- -p 3000

# 3) 测量脚本(gitignored)
backend/.pytest_tmp/tb_perf_final.js            # A/B/C/D 四档(清 SW + 断言 rowsReady + 光标确证)
backend/.pytest_tmp/tb_perf_crosshair_verify.js  # C 档复核(带光标触发确证)
backend/.pytest_tmp/tb_click_attrib.js           # 切票归因(长任务 vs 资源时序)
backend/.pytest_tmp/tb_loaf_attrib.js            # LoAF 脚本级归因
backend/.pytest_tmp/tb_canvas_resize_probe.js    # canvas 尺寸变化探针(证伪 RO 反馈循环)
backend/.pytest_tmp/tb_crosshair_isolate.js       # 对照实验:光标 vs 自动刷新
```

> 跑任何一档之前,先确认 **① 列表真的有行(`rowsReady`)② rAF 帧率正常**,
> 否则数字不作数(见 §7)。
